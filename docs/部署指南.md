# 极简简历 MiniWho 部署指南

本文覆盖本地开发、手工生产部署、Docker 部署（官方镜像或源码构建）、MySQL、Nginx、HTTPS、数据备份与常见故障。接口细节见 [API 文档](API.md)，功能操作见 [使用教程](使用教程.md)。

> 当前版本是单实例应用：Sa-Token 默认将会话保存在后端进程内存中，后端重启后用户需要重新登录；附件默认存本地磁盘。若要横向扩容，需要先接入共享会话存储与对象存储。

---

## 1. 架构与运行依赖

```text
浏览器
  │
  ├── :5173 (开发) Vite ── /api 代理 ──┐
  │                                     ▼
  └── :8088 (Docker) 单镜像 ────────── Spring Boot :8080
        （前端静态资源 + /api + SPA 回落）  │
                                         ├── SQLite 文件 或 MySQL 8
                                         ├── uploads/ 附件与照片目录
                                         └── 无头 Chrome/Edge ── 渲染 /export/:token ──┐
                                                                                      ▼
                                                                       uploads/exports/*.pdf 下载
```

Docker 部署只有**一个应用镜像**：前端构建产物在打包阶段放进 jar 的 `static/`，由 Spring Boot 直接提供页面、静态资源与 `/api`，前端路由（如 `/dashboard`、`/export/:token`）找不到文件时回落到 `index.html`。手工部署仍然可以让 Nginx 托管 `dist/`，两条路都支持。

| 组件 | 要求 |
| --- | --- |
| JDK | 17 或更高 |
| Maven | 3.8+ |
| Node.js | 18+，推荐 20 / 22 |
| 数据库 | SQLite（默认，零配置）或 MySQL 8 |
| 反向代理 | 生产环境推荐 Nginx |
| 无头浏览器 | 可选，Chrome / Edge / Chromium；服务端 PDF 导出需要，缺失时前端自动回退到浏览器打印 |
| 中文字体 | 服务端 PDF 需要，Linux 建议 `fonts-noto-cjk`，缺失时中文会变成方块 |
| Docker | 可选，Docker 24+ / Compose v2；直接使用官方镜像 `cosolar/miniwho` 时不需要 JDK / Maven / Node，镜像已内置 Chromium 与 Noto CJK |

默认端口：后端 `8080`，Vite 开发服务器 `5173`，Compose 应用 `8088`。

## 2. 本地开发

### 2.1 SQLite 模式（最快）

```bash
cd backend
MINIWHO_ADMIN_PASSWORD=admin123 mvn spring-boot:run
```

首次启动会在**当前工作目录**创建：

- `backend/miniwho.db`：SQLite 数据库；
- `backend/uploads/`：附件、简历照片（`avatars/`）与条目 LOGO（`media/{resumeId}/`）目录，换服务器时整个目录要一起搬；
- 12 套模板、`demo` / `admin` 演示账号和一份示例简历。

管理员密码没有默认值：库里还没有 `admin` 账号且未设置 `MINIWHO_ADMIN_PASSWORD` 时，应用会拒绝启动并提示设置。Windows PowerShell 用 `$env:MINIWHO_ADMIN_PASSWORD="admin123"` 设置后再 `mvn spring-boot:run`。

验证后端：

```bash
curl http://localhost:8080/api/health
# {"code":"OK","message":"ok","data":{"app":"miniwho","status":"UP",...}}
```

另开终端启动前端：

```bash
cd frontend
npm install
npm run dev
```

打开 `http://localhost:5173`，用 `demo / demo123` 或 `admin / <你设置的 MINIWHO_ADMIN_PASSWORD>` 登录。

开发模式下，如果本机装有 Chrome / Edge 且 Vite 已启动，服务端 PDF 可以直接工作：`MINIWHO_PDF_RENDER_BASE_URL` 默认就是 `http://127.0.0.1:5173`，后端会用它打开导出页面。确认引擎状态（该接口需要登录令牌）：

```bash
curl -H "satoken: <登录后拿到的令牌>" http://localhost:8080/api/pdf/status
# {"code":"OK","data":{"available":true,"engine":"chrome-headless"}}
```

前端「预览导出」页会读取同一状态：引擎不可用时按钮自动退回浏览器打印，不会报错卡死。

开发模式下 Vite 将 `/api` 代理到 `http://localhost:8080`。如果后端不在默认地址，复制 `frontend/.env.example` 为 `frontend/.env.local` 并修改：

```dotenv
VITE_API_BASE=/api
VITE_PROXY_TARGET=http://127.0.0.1:8080
```

### 2.2 MySQL 8 模式

先创建数据库和专用账号（不要直接使用 root 跑生产）：

```sql
CREATE DATABASE miniwho CHARACTER SET utf8mb4 COLLATE utf8mb4_unicode_ci;
CREATE USER 'miniwho'@'%' IDENTIFIED BY '替换成强密码';
GRANT ALL PRIVILEGES ON miniwho.* TO 'miniwho'@'%';
FLUSH PRIVILEGES;
```

然后带 `mysql` profile 启动：

```bash
cd backend
SPRING_PROFILES_ACTIVE=mysql \
DB_HOST=127.0.0.1 DB_PORT=3306 DB_NAME=miniwho \
DB_USER=miniwho DB_PASSWORD='替换成强密码' \
mvn spring-boot:run
```

Windows PowerShell 可先设置环境变量再启动：

```powershell
$env:SPRING_PROFILES_ACTIVE = "mysql"
$env:DB_HOST = "127.0.0.1"
$env:DB_NAME = "miniwho"
$env:DB_USER = "miniwho"
$env:DB_PASSWORD = "替换成强密码"
mvn spring-boot:run
```

`application-mysql.yml` 会在启动时执行 `db/schema-mysql.sql`（`CREATE TABLE IF NOT EXISTS`）。数据库本身需要提前创建，应用不会自动 `CREATE DATABASE`。

### 2.3 演示数据开关

| 变量 | 默认值 | 作用 |
| --- | --- | --- |
| `MINIWHO_SEED_DEMO` | `true` | 是否创建 `demo`、`admin`、示例简历与一条示例反馈 |
| `MINIWHO_DEMO_PASSWORD` | `demo123` | `demo` 首次创建时的密码 |
| `MINIWHO_ADMIN_PASSWORD` | 无（必填） | `admin` 首次创建时的密码；库里还没有 admin 且未设置时应用拒绝启动 |

注意：

- 密码变量只在账号**第一次创建**时生效。账号已存在时再次修改环境变量不会改密码。
- `MINIWHO_ADMIN_PASSWORD` 在 `MINIWHO_SEED_DEMO=true` 且库里还没有 `admin` 账号时必须提供；账号已存在后可以不再设置。
- 仍填示例值 `admin123` 时启动只打 WARN 不拦截，公网部署前请务必更换。
- `MINIWHO_SEED_DEMO=false` 只是停止后续初始化，不会删除已经创建的 demo / admin 和示例数据。
- 生产环境不要保留默认密码。最稳妥的做法是首次启动时通过环境变量设置强密码，登录后在「个人中心」再次修改。

### 2.4 注册方式、邮件与 GitHub 登录

登录页有三种入口：**用户名注册**、**邮箱验证码注册**、**GitHub 登录**。它们各自要同时满足两个条件才会出现在前台：

1. 管理员在后台「认证设置」里打开了对应开关；
2. 对应的通道凭据配置齐了（通道真的可用）。

开关是意愿，凭据就绪才是事实。凭据缺失时后台会显示「未配置」并列出缺哪几项，前台不会渲染出点不开的按钮。

> **默认状态是三个开关全关。** 只配好 SMTP / GitHub 凭据还不够，必须进后台把开关打开；反过来，什么都没配的部署不提供任何自助注册，只能由管理员建号（首次部署的顺序见 3.1 节末尾）。这是防乱注册的默认姿态，不是漏配。

##### 凭据有两种配法，后台填的优先

下面每一组凭据都能**不重启、不改 compose** 直接在后台 `/admin` → 认证设置 → 通道配置里填，保存后下一次发信 / 下一次登录就用新值。取值规则按项判定：

- 后台填过这一项 → 用后台的；
- 后台这一项是空的（从没填过，或点了「清空并回落到环境变量」）→ 用对应环境变量的；
- 于是两种来源能混着用，比如 host 与署名走环境变量，只把授权码填在后台。

后台面板上每张卡片都会写明当前值来自哪里（「当前由后台配置」/「当前值来自环境变量」），改哪一方一目了然。邮箱授权码与 GitHub Client secret 只写不读：保存后界面上只剩「已保存」占位，`PUT` 时留空表示不改这一项。

**这些值在 `site_settings` 表里是明文存的。** 图的是改起来快、不依赖任何加密配置，代价是谁能读到这个库谁就拿到了你的邮箱授权码。数据库别暴露到公网、别把库文件或与库同目录的备份传到公开地方；介意的话就只用环境变量，后台留空即可。

#### 邮箱注册（SMTP）

只支持标准 SMTP，不接任何第三方发信服务。以 QQ 邮箱为例：

1. 网页登录 QQ 邮箱 → 设置 → 账号与安全 → 开启 **IMAP/SMTP 服务**，按提示用绑定的手机号验证后拿到一串 16 位**授权码**；
2. 填凭据，二选一：在后台「通道配置 → 邮件通道」里填主机 `smtp.qq.com`、端口 `465`、发件地址 `你的号@qq.com`、授权码，保存即生效；或填环境变量 `MINIWHO_MAIL_HOST` / `_PORT` / `_FROM` / `_PASSWORD`；
3. `MINIWHO_MAIL_USERNAME` 可以不填，缺省取发件地址；`MINIWHO_MAIL_SSL` 保持 `true`。

163 邮箱同理：`smtp.163.com`、465 端口、`MINIWHO_MAIL_PASSWORD` 填「设置 → POP3/SMTP/IMAP」里生成的客户端授权密码。

下表的每一项都有同名的后台字段，环境变量只是「后台没填时」的默认来源：

| 变量 | 默认值 | 说明 |
| --- | --- | --- |
| `MINIWHO_MAIL_HOST` | 空 | 留空即视为通道未配置，邮箱注册开关打了也不生效 |
| `MINIWHO_MAIL_PORT` | `465` | 465 用隐式 SSL |
| `MINIWHO_MAIL_USERNAME` | 空（取 `MINIWHO_MAIL_FROM`） | SMTP 登录名 |
| `MINIWHO_MAIL_PASSWORD` | 空 | **授权码**，不是邮箱登录密码 |
| `MINIWHO_MAIL_FROM` | 空 | 发件地址，需与授权账号一致 |
| `MINIWHO_MAIL_FROM_NAME` | `极简简历` | 收件人看到的署名，中文按 RFC 2047 编码 |
| `MINIWHO_MAIL_SSL` | `true` | 隐式 SSL |
| `MINIWHO_MAIL_STARTTLS` | `false` | 587 之类改成 `MINIWHO_MAIL_SSL=false` + 本项 `true` |

验证码链路的行为（写在这里是为了排查「用户说收不到」时对得上）：

- 6 位数字，10 分钟有效；库里只存 bcrypt 哈希，验证通过立刻删除，同一封验证码最多试错 5 次。
- 同一邮箱 60 秒内不能重发，每小时最多 5 封；此外还有按 IP 的公开接口限流。过期超过 24 小时的记录在下次发信时顺带清理。
- 邮箱在库里是唯一索引：已被占用的邮箱直接回「该邮箱已注册，请直接登录」。**没有找回密码功能**，忘记密码目前只能由管理员在数据库里重置。
- SMTP 对端无响应不会挂住业务线程：连接超时 5 秒、读写超时 10 秒，失败返回 502，日志里只记失败原因、不记收件地址。
- 用邮箱注册的账号，`email_verified` 直接是 1——它本来就是验证码确认过的。

#### GitHub 登录

在 GitHub 的 **Settings → Developer settings → OAuth Apps → Register a new application** 里建应用：

- **Authorization callback URL** 填 `https://<你的域名>/api/auth/oauth/github/callback`，后台「认证设置」页面会把这一条原样显示出来并提供复制，直接抄过去最稳；
- Application name / Homepage URL 随意，H 没有；勾选后保存，拿到 Client ID 和新生成的 Client secret。

```dotenv
MINIWHO_PUBLIC_BASE_URL=https://resume.example.com
MINIWHO_GITHUB_CLIENT_ID=替换成 Client ID
MINIWHO_GITHUB_CLIENT_SECRET=替换成 Client secret
```

`MINIWHO_PUBLIC_BASE_URL` 是站点对外的完整地址（末尾不带斜杠），GitHub 的回调地址和登录完成后送回前端的位置都从它拼出来。留空则 GitHub 通道视为未配置。反向代理部署时要填代理**对外**的那个 `https://域名`，不是 `127.0.0.1:8080`。

这三项同样能在后台「通道配置 → GitHub OAuth」里填，填完这一张卡片就会显示「当前由后台配置」，回调地址随之刷新；凭据齐了才允许把「GitHub 登录」开关打开，同一次保存里一起提交也行。

行为要点：

- 授权作用域只有 `read:user user:email`，只取 GitHub 的**主邮箱**；存进库的是 GitHub 用户 ID、用户名、昵称、头像和那个邮箱。
- 首次登录自动建号并自动创建第一份简历，用户名是 `github_<GitHub 用户名>`，密码位是随机占位哈希且 `has_password=0`——这类账号没有可用密码，个人中心那一栏显示「登录方式」而不是修改密码。
- 只有当本地账号的邮箱是**验证码验证过**的，才会自动关联；存量库里手工填的、没验证过的邮箱一律不认，避免有人抢注别人的邮箱接管账号。
- 令牌用 URL 片段（`/login#satoken=...`）交回前端，服务端不落日志，前端读到手立刻从地址栏抹掉；`state` 是一次性的内存值，10 分钟过期、只能核销一次，重放或伪造都直接送回登录页报错。
- 用户在 GitHub 页面点取消、或同一个回调链接被重复打开，都只是失败：浏览器导航渲染不了 JSON，统一 302 回 `/login#oauth_error=1` 由前端提示。

#### 后台「认证设置」接口

| 接口 | 说明 |
| --- | --- |
| `GET /api/admin/settings` | 三个开关的当前值 + `mailConfigured` / `githubConfigured` + 回调地址回显 + `mail` / `github` 两组当前生效的通道配置（含「来自后台还是环境变量」） |
| `PUT /api/admin/settings` | 只提交要改的项，未提交的保持不变；字符串传空串表示清空该项并回落到环境变量。字段级契约见 API.md 10.10 |
| `GET /api/public/auth-config` | 登录页读取的实际可用入口，无需鉴权，响应带 30 秒 `private` 缓存 |

凭据与开关都是保存即生效，后端不用重启；只有 `state`（GitHub 登录的一次性值）存在进程内存里，重启后未完成的授权会失效。因为最后一项有 30 秒缓存，管理员改完开关后登录页最多 30 秒才变；后台保存时会把这句话提示给用户，别当成没保存成功。

## 3. 手工生产部署

### 3.1 构建后端

```bash
cd backend
mvn clean package -DskipTests
# 产物：backend/target/miniwho-1.0.2.jar
```

建议生产使用 MySQL，并为上传目录使用独立、可备份的位置：

```bash
sudo mkdir -p /opt/miniwho/backend /opt/miniwho/uploads
sudo useradd --system --home /opt/miniwho --shell /usr/sbin/nologin miniwho
sudo cp backend/target/miniwho-1.0.2.jar /opt/miniwho/backend/
sudo chown -R miniwho:miniwho /opt/miniwho
```

`/etc/miniwho/miniwho.env`：

```dotenv
SPRING_PROFILES_ACTIVE=mysql
DB_HOST=127.0.0.1
DB_PORT=3306
DB_NAME=miniwho
DB_USER=miniwho
DB_PASSWORD=替换成强密码
MINIWHO_UPLOAD_DIR=/opt/miniwho/uploads
MINIWHO_CORS_ORIGINS=https://resume.example.com
MINIWHO_SEED_DEMO=false
SERVER_PORT=8080
MINIWHO_MEDIA_SECRET=替换成随机长字符串
MINIWHO_PDF_RENDER_BASE_URL=http://127.0.0.1
# 注册 / 登录方式（可选：这里留空也能改在后台「认证设置 → 通道配置」里填，保存即生效；开关本身在后台，见 2.4）
MINIWHO_PUBLIC_BASE_URL=https://resume.example.com
MINIWHO_MAIL_HOST=smtp.qq.com
MINIWHO_MAIL_FROM=你的号@qq.com
MINIWHO_MAIL_PASSWORD=替换成邮箱授权码
MINIWHO_GITHUB_CLIENT_ID=替换成 GitHub OAuth App 的 Client ID
MINIWHO_GITHUB_CLIENT_SECRET=替换成 Client secret
```

`MINIWHO_MEDIA_SECRET` 用于给简历照片生成带签名的临时链接（有效期 6 小时）。留空时后端每次启动随机生成一把密钥，重启后旧的照片链接全部失效，多实例之间也无法互认，生产环境请显式配置一个 32 位以上的随机值：

```bash
openssl rand -hex 32
```

`MINIWHO_PDF_RENDER_BASE_URL` 是后端调用无头浏览器时访问的前端地址，必须是**后端进程自身可达**的地址，且不需要登录。同机部署时优先使用明文 HTTP 的内网地址（例如 Nginx 额外监听 `127.0.0.1:8088` 指向同一份 `dist/`）；只走自签 HTTPS 时证书校验可能失败，导致导出报错。

#### 服务端 PDF 依赖（可选）

不装也能跑，前端会自动回退到「浏览器打印 → 另存为 PDF」。装上后可一键下载排版一致的 PDF：

```bash
# Debian / Ubuntu
sudo apt install -y chromium fonts-noto-cjk

# Alpine
apk add --no-cache chromium font-noto-cjk

# CentOS / RHEL / Rocky
sudo dnf install -y chromium google-noto-sans-cjk-ttc-fonts
```

```bash
# 确认后端找得到浏览器，然后重启服务
which chromium chromium-browser google-chrome microsoft-edge
sudo systemctl restart miniwho
curl -H "satoken: <登录令牌>" http://127.0.0.1:8080/api/pdf/status
```

Windows 部署无需额外安装，后端会直接探测 Chrome / Edge 的默认安装路径；只有两者都不在标准位置时才设置 `MINIWHO_PDF_BROWSER_PATH` 指向可执行文件。

systemd 服务 `/etc/systemd/system/miniwho.service`：

```ini
[Unit]
Description=MiniWho backend
After=network.target

[Service]
User=miniwho
Group=miniwho
WorkingDirectory=/opt/miniwho/backend
EnvironmentFile=/etc/miniwho/miniwho.env
ExecStart=/usr/bin/java -Xms256m -Xmx512m -jar /opt/miniwho/backend/miniwho-1.0.2.jar
Restart=on-failure
RestartSec=5
NoNewPrivileges=true
PrivateTmp=true

[Install]
WantedBy=multi-user.target
```

```bash
sudo systemctl daemon-reload
sudo systemctl enable --now miniwho
sudo systemctl status miniwho
sudo journalctl -u miniwho -f
```

如果 `MINIWHO_SEED_DEMO=false` 且数据库中还没有管理员，注意此时**没有任何自助注册入口**（三个开关默认全关，见 2.4），所以先把管理员账号建出来，再打开需要的注册方式：

```sql
-- MySQL：临时用 seed 起一次最省事，也可以照下面手工插一个 admin（密码需另设，见下）
UPDATE users SET role = 'admin', updated_at = UNIX_TIMESTAMP() * 1000 WHERE username = '你的用户名';
```

最省事的顺序是：首次启动保持 `MINIWHO_SEED_DEMO=true` 并设置 `MINIWHO_ADMIN_PASSWORD`，登录 `/admin` 后在「认证设置」里按需打开注册方式（凭据没配的用户名注册也可以只开它一项），确认没问题再把 `MINIWHO_SEED_DEMO` 改回 `false`。

如果只想留 SQLite / MySQL 里的一条记录，直接给 `site_settings` 插开关也可以，但要**重启应用**才生效——开关读进内存后有缓存：

```sql
INSERT INTO site_settings (setting_key, setting_value, updated_at)
VALUES ('register_username', 'true', UNIX_TIMESTAMP() * 1000);
```

退出并重新登录后，即可访问 `/admin`。

> SQLite 模式同理，可用 `sqlite3 miniwho.db` 执行相同更新。不要直接手改密码哈希；忘记密码时，优先由管理员在页面中处理账号状态，或重建账号。

### 3.2 构建前端

```bash
cd frontend
npm ci
npm run build
# 产物：frontend/dist/
```

如果不想再单独跑一层静态站点，也可以把 `dist/` 直接打进后端 jar（Docker 镜像就是这个流程）：

```bash
rm -rf backend/src/main/resources/static
cp -r frontend/dist backend/src/main/resources/static
cd backend && mvn -DskipTests package
```

`StaticSiteConfig` 会接管静态资源：`/assets/**` 长缓存、其余文件 `no-cache`、没有扩展名的路径回落到 `index.html`，`/api/**` 仍走接口。运行这个 jar 时把 `MINIWHO_PDF_RENDER_BASE_URL` 指向它自己的端口（默认 `http://127.0.0.1:8080`）即可服务端导出 PDF。

把 `dist/` 内容发布到 Nginx 站点目录：

```bash
sudo mkdir -p /var/www/miniwho
sudo rsync -a --delete frontend/dist/ /var/www/miniwho/
```

默认 `VITE_API_BASE=/api`，由 Nginx 反向代理到后端。项目默认部署在域名根路径；如需部署到 `/resume/` 子路径，需要同时修改 Vite `base`、Vue Router history base 与 Nginx `try_files`，当前版本未内置该配置。

上线前想在本地验证构建产物，可以让后端与静态站点分别启动（`VITE_API_BASE` 在构建期注入，`preview` 只读取已构建的产物，所以必须先构建再预览）：

```bash
# 终端 1：后端，把预览地址加入允许跨域的来源
cd backend
MINIWHO_CORS_ORIGINS=http://localhost:4173 java -jar target/miniwho-1.0.2.jar

# 终端 2：生产构建 + 静态预览
cd frontend
VITE_API_BASE=http://localhost:8080/api npm run build
npm run preview -- --port 4173
```

浏览器打开 `http://localhost:4173`，此时不经过开发服务器的 `/api` 代理，走的正是生产构建 + 跨域请求路径。验证完记得用默认配置重新 `npm run build`，否则产物里会留下绝对地址。

### 3.3 Nginx 反向代理

本站品牌域名为 `who.minims.cn`（页脚与 LOGO 上的署名）；下面的 `server_name` 换成你自己实际解析的域名即可。

`/etc/nginx/conf.d/miniwho.conf`：

```nginx
server {
    listen 80;
    server_name resume.example.com;

    root /var/www/miniwho;
    index index.html;
    charset utf-8;
    client_max_body_size 25m;

    gzip on;
    gzip_min_length 1024;
    gzip_comp_level 5;
    gzip_types text/plain text/css application/json application/javascript application/xml image/svg+xml;

    add_header X-Content-Type-Options nosniff always;
    add_header Referrer-Policy strict-origin-when-cross-origin always;
    add_header X-Frame-Options SAMEORIGIN always;

    location /api/ {
        proxy_pass http://127.0.0.1:8080;
        proxy_http_version 1.1;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
        proxy_read_timeout 60s;
        proxy_send_timeout 60s;
    }

    location /assets/ {
        expires 30d;
        add_header Cache-Control "public, immutable";
        try_files $uri =404;
    }

    location = /index.html {
        add_header Cache-Control "no-cache";
    }

    location / {
        try_files $uri $uri/ /index.html;
    }
}
```

```bash
sudo nginx -t
sudo systemctl reload nginx
```

要点：

- `try_files ... /index.html` 是 Vue Router history 模式刷新不 404 的必要配置。
- `client_max_body_size` 不能小于附件上传上限（后端请求上限 25MB）。
- 后端 `8080` 只需监听本机或内网，不要直接暴露公网。
- 反向代理会改写请求的 Host，后端可能把同源请求也判成跨域；`MINIWHO_CORS_ORIGINS` 默认 `*`（放行任意来源、不携带 Cookie），通过自定义域名访问无需额外配置。仅在需要收紧时填写具体来源，多个源用逗号分隔。

### 3.4 HTTPS

使用 Certbot 为例：

```bash
sudo apt install certbot python3-certbot-nginx
sudo certbot --nginx -d resume.example.com
```

证书生效后确认：

- HTTP 自动跳转 HTTPS；
- 如果把 `MINIWHO_CORS_ORIGINS` 收紧为白名单，条目必须使用 `https://` 开头；
- 确认站点无异常后再考虑添加 HSTS；
- 分享链接也必须是 HTTPS，避免密码与简历内容明文传输。

### 3.5 可选：登录与注册接口再加一层限流

应用后端已按 IP 内置限流（每分钟：登录 10 次、用户名注册与邮箱注册各 5 次、验证码 5 次、GitHub 跳转与回调合计 20 次、分享解锁 10 次、统计 120 次），超出返回 429；邮箱验证码另外还按邮箱限到 60 秒 1 封 / 每小时 5 封。应用本身没有图形验证码，公网大流量场景建议在 Nginx 再叠一层：

```nginx
limit_req_zone $binary_remote_addr zone=miniwho_auth:10m rate=10r/m;

server {
    # ...
    location = /api/auth/login {
        limit_req zone=miniwho_auth burst=5 nodelay;
        proxy_pass http://127.0.0.1:8080;
        include proxy_params;
    }
    location = /api/auth/email-code {
        limit_req zone=miniwho_auth burst=2 nodelay;
        proxy_pass http://127.0.0.1:8080;
        include proxy_params;
    }
}
```

如果使用发行版默认的 `proxy_params`，请确认其中包含必要的转发头；也可以复制上一节 `/api/` 的完整代理配置。

> 内置限流认的是 `X-Forwarded-For` 的第一跳，没有该头时退回直连地址。反向代理必须转发 `X-Forwarded-For`，否则所有请求在应用眼里都是代理机那一个 IP，限流会变成「整站一起被限」。

## 4. Docker 部署

两条路，产物都是同一个单镜像（前端页面 + 后端 API + 无头 Chromium + Noto CJK 字体，页面与 `/api` 同端口、同源）：

| 方式 | 适合谁 | 本机需要 | 耗时 |
| --- | --- | --- | --- |
| 4.1 直接拉取已发布镜像 `cosolar/miniwho` | 只想把站跑起来（推荐） | 只要 Docker | 几分钟（下载约 552MB） |
| 4.2 从仓库源码构建 | 改过代码、要自己出镜像 | Docker + 构建用的网络与 CPU | 首次构建约 5–10 分钟 |

两种方式的数据都放在 Docker named volume 里，升级只换镜像、不丢数据；备份与升级见第 5 节。

### 4.1 使用已发布镜像

镜像发布在 Docker Hub：`cosolar/miniwho`。标签跟着 git tag 走，最新版有 `1.0.2`、`1.0`、`latest`（三者同一 digest）；`1.0.1` 这类旧版本号固定在当初那次发布上，不会再跟着更新。**只提供 `linux/amd64`**，Apple Silicon（arm64）机器需要加 `--platform linux/amd64` 走模拟。

```bash
docker pull cosolar/miniwho:1.0.2
```

想确认某个标签对应哪次提交：

```bash
docker inspect --format '{{ index .Config.Labels "org.opencontainers.image.revision" }}' cosolar/miniwho:1.0.2
```

#### 4.1.1 Compose + MySQL 8（生产推荐）

不需要 clone 仓库，新建一个目录放 compose 文件即可：

```bash
mkdir -p /opt/miniwho && cd /opt/miniwho
```

`docker-compose.yml`：

```yaml
services:
  mysql:
    image: mysql:8.4
    restart: unless-stopped
    environment:
      MYSQL_ROOT_PASSWORD: "替换成 root 强密码"
      MYSQL_DATABASE: miniwho
      MYSQL_USER: miniwho
      MYSQL_PASSWORD: "替换成业务强密码"
      TZ: Asia/Shanghai
    command:
      - --character-set-server=utf8mb4
      - --collation-server=utf8mb4_unicode_ci
    volumes:
      - mysql-data:/var/lib/mysql
    healthcheck:
      test: ["CMD-SHELL", "mysqladmin ping -h 127.0.0.1 -u root -p$$MYSQL_ROOT_PASSWORD --silent"]
      interval: 10s
      timeout: 5s
      retries: 12
      start_period: 30s

  app:
    image: cosolar/miniwho:1.0.2
    restart: unless-stopped
    environment:
      SPRING_PROFILES_ACTIVE: mysql
      DB_HOST: mysql
      DB_PORT: "3306"
      DB_NAME: miniwho
      DB_USER: miniwho
      DB_PASSWORD: "替换成业务强密码"
      MINIWHO_UPLOAD_DIR: /app/uploads
      MINIWHO_MEDIA_SECRET: "替换成 openssl rand -hex 32 的输出"
      MINIWHO_ADMIN_PASSWORD: "替换成管理员强密码"
      MINIWHO_DEMO_PASSWORD: "替换成演示账号强密码"
      MINIWHO_CORS_ORIGINS: "*"
      TZ: Asia/Shanghai
    shm_size: "512mb"
    volumes:
      - uploads:/app/uploads
    depends_on:
      mysql:
        condition: service_healthy
    ports:
      - "8088:8080"
    healthcheck:
      test: ["CMD-SHELL", "wget -qO- http://127.0.0.1:8080/api/health || exit 1"]
      interval: 15s
      timeout: 5s
      retries: 10
      start_period: 40s

volumes:
  mysql-data:
  uploads:
```

```bash
docker compose up -d
docker compose ps
curl -fsS http://127.0.0.1:8088/api/health
```

要点：

- 应用连上 MySQL 后会自动执行 `CREATE TABLE IF NOT EXISTS` 建表，并写入 12 套官方模板。`MYSQL_USER` 对 `miniwho` 库拥有全部权限，`SchemaMigrator` 启动补列所需的 `ALTER` 权限已经满足。
- `app` 等 MySQL 健康检查通过才启动；MySQL 首次初始化通常要 30–60 秒，`docker compose ps` 里 `app` 短暂 `Created` 是正常的。
- 页面与 `/api` 共用 `8088`，同源，不涉及跨域；换域名 / IP 访问也不用改 `MINIWHO_CORS_ORIGINS`（默认 `*`，认证走 `satoken` 请求头、不携带 Cookie）。要收紧时填逗号分隔的具体来源。
- `MINIWHO_MEDIA_SECRET` 必须填固定值，否则应用每次重启后历史头像链接全部失效。用 `openssl rand -hex 32` 生成。
- `MINIWHO_ADMIN_PASSWORD` / `MINIWHO_DEMO_PASSWORD` 只在账号**第一次创建**时生效；首次启动后立刻在「个人中心 → 修改密码」再改一次。
- **注册入口默认全关**：这样部署出来就是一个纯自用的站。要让别人自助注册，登录后门 `/admin` → 认证设置按需打开（邮箱注册要先把邮件通道配好，GitHub 登录要先把 Client ID / Secret 与站点对外地址配好；这两组凭据既能直接在同一页的「通道配置」里填，也能用 `MINIWHO_MAIL_*` / `MINIWHO_GITHUB_*` / `MINIWHO_PUBLIC_BASE_URL`，见 2.4）。
- 服务端 PDF 开箱可用：镜像内置 Chromium 与中文字体。`MINIWHO_PDF_RENDER_BASE_URL` 已固定为 `http://127.0.0.1:8080`（无头浏览器访问的就是同一个容器里的页面），不要改成别的主机名或容器名。
- 内存：PDF 峰值约 600MB–1GB（默认最多同时渲染 2 份），给容器至少 1GB 上限；`shm_size: "512mb"` 不要删，Chromium 需要共享内存。

#### 4.1.2 单容器 + 内置 SQLite（最快试跑）

不想装 MySQL 时一个容器就能跑，数据库用镜像内置的 SQLite：

```bash
docker run -d --name miniwho \
  -p 8088:8080 \
  -v miniwho-uploads:/app/uploads \
  -e MINIWHO_DB=/app/uploads/miniwho.db \
  -e MINIWHO_ADMIN_PASSWORD='替换成管理员强密码' \
  -e MINIWHO_DEMO_PASSWORD='替换成演示账号密码' \
  -e MINIWHO_MEDIA_SECRET="$(openssl rand -hex 32)" \
  -e TZ=Asia/Shanghai \
  --shm-size=512m \
  cosolar/miniwho:1.0.2
```

- `MINIWHO_DB` 这一行不能省：默认值是 `./miniwho.db`，在容器里就是 `/app/miniwho.db`——可写，但不在卷里，`docker rm` 之后数据库跟着容器一起消失。
- 容器以非 root 用户 `app` 运行；用 named volume 时权限由 Docker 初始化，无需手工 `chown`。
- SQLite 适合个人自用、单实例部署；多人并发写入（尤其是导出 PDF 时）建议用上面的 MySQL。
- 数据库与附件都在 `miniwho-uploads` 卷里，备份时整个卷打走即可：

```bash
docker run --rm \
  -v miniwho-uploads:/data:ro \
  -v "$PWD":/backup \
  alpine tar czf /backup/miniwho-$(date +%F).tar.gz -C /data .
```

#### 4.1.3 镜像里已经定好的东西

| 项目 | 值 | 说明 |
| --- | --- | --- |
| 运行用户 | `app`（非 root） | bind mount 宿主机目录时，目录要对这个用户可写；named volume 不用管 |
| 工作目录 | `/app` | SQLite 默认相对路径的参照点 |
| 内置浏览器 | `/usr/bin/chromium` | `MINIWHO_PDF_BROWSER_PATH` 已预设，不需要再装 Chrome |
| 中文字体 | Noto CJK | 导出的 PDF 中文不会变成方块 |
| PDF 渲染地址 | `http://127.0.0.1:8080` | 单镜像自带前端页面；只有把页面拆到别的域名 / 容器才需要改 |
| 监听端口 | `8080` | 宿主机端口随意映射，例如 `-p 8088:8080` |
| 时区 | 未固定 | 建议 `TZ=Asia/Shanghai`，与后端的 `Asia/Shanghai` 保持一致 |
| CPU 架构 | `linux/amd64` | 没有 arm64 镜像 |

首次登录、演示数据开关、停止与清理见 4.3 / 4.4。

### 4.2 从仓库源码构建

仓库自带 `docker-compose.yml`：MySQL 8.4 + **一个应用镜像**（前端页面 + 后端 API，产物打进同一个 jar）。MySQL 数据与上传目录使用 named volume，只有应用容器对外暴露端口。

镜像构建在仓库根目录进行（`Dockerfile` 有三阶段）：Node 构建 `frontend/dist` → Maven 把它放进 `backend/src/main/resources/static` 后打包 → 运行阶段用带 Chromium 与 Noto CJK 的 JRE 镜像。所以**前端产物随 jar 发布，不需要单独的前端容器或 Nginx**。

#### 4.2.1 启动

在仓库根目录操作。`docker compose up -d --build` 会现场构建镜像，产物与 4.1 拉下来的是同一套三阶段结果：

```bash
cp .env.example .env
```

至少修改 `.env` 中以下值：

```dotenv
MINIWHO_ADMIN_PASSWORD=请替换

MINIWHO_MEDIA_SECRET=请替换成随机长字符串
```


访问 `http://localhost:8088`。健康状态：

镜像内已内置 Chromium 与 Noto CJK 字体，`MINIWHO_PDF_RENDER_BASE_URL` 默认是 `http://127.0.0.1:8080`——无头浏览器访问的就是同一个容器里的页面，因此**服务端 PDF 与简历照片开箱可用**。`MINIWHO_MEDIA_SECRET` 留空时照片签名链接会在应用重启后失效，建议每次都填。

### 4.3 首次登录与关闭演示数据

1. 保持 `MINIWHO_SEED_DEMO=true` 首次启动，用环境变量里设置的 `admin` 密码登录（源码构建方式在 `.env`，官方镜像方式在 compose 或 `docker run -e` 里）。
2. 立即在「个人中心 → 修改密码」更换密码。
3. 决定要不要让别人自助注册：进 `/admin` → 「认证设置」。**三个开关出厂都是关的**，什么都不动就是一个只能自己用的站；要开放邮箱注册或 GitHub 登录，先把 2.4 的凭据配好再打开对应开关。
4. 确认不再需要演示内容后，可将 `MINIWHO_SEED_DEMO` 改为 `false` 并重启容器 / 后端。
5. 该开关不会删除已经存在的 `demo` 账号和示例简历；如需彻底移除，请在数据库中删除或禁用对应账号。

如果不希望首次创建演示账号：

- 设置 `MINIWHO_SEED_DEMO=false`；
- 在前端注册第一个普通账号；
- 进入 MySQL 将其 `role` 改为 `admin`：

```bash
docker compose exec mysql mysql -uroot -p miniwho
```

```sql
UPDATE users SET role = 'admin', updated_at = UNIX_TIMESTAMP() * 1000 WHERE username = '你的用户名';
```

重新登录后访问 `/admin`。

单容器 + SQLite 部署的镜像里没有 `sqlite3` 命令行，建议首次先保持 `MINIWHO_SEED_DEMO=true` 把 `admin` 建出来，再改为 `false` 重启；确实需要手工改库时，把 `miniwho-uploads` 卷里的 `miniwho.db` 复制到宿主机，用宿主机的 `sqlite3` 修改后再放回。

### 4.4 停止与清理

Compose 部署：

```bash
docker compose stop          # 停止容器，保留数据
docker compose down          # 删除容器与网络，保留 named volume
docker compose down -v       # 连数据一起删除，危险，仅用于彻底重置
```

单容器部署：

```bash
docker stop miniwho              # 停止容器，保留数据
docker rm miniwho                # 删除容器，named volume 不受影响
docker volume rm miniwho-uploads # 连数据库与附件一起删除，危险
```

`docker compose down -v` 与 `docker volume rm` 都会永久删除数据（MySQL 数据、SQLite 数据库与上传附件），执行前务必备份。

## 5. 备份、恢复与升级

### 5.1 SQLite（手工部署）

SQLite 使用 WAL 模式，最稳妥的备份方式：

```bash
# 方案 A：在线备份
sqlite3 /opt/miniwho/backend/miniwho.db ".backup '/backup/miniwho-$(date +%F).db'"

# 方案 B：短暂停机后复制
sudo systemctl stop miniwho
cp /opt/miniwho/backend/miniwho.db* /backup/
sudo systemctl start miniwho
```

同时备份附件目录：

```bash
tar czf /backup/miniwho-uploads-$(date +%F).tar.gz -C /opt/miniwho uploads
```

`uploads/` 下的 `avatars/`（简历照片）与附件同样重要，但 `exports/` 只是 PDF 结果缓存，删除后下次导出会重新渲染，备份前可以先排除：

```bash
tar czf /backup/miniwho-uploads-$(date +%F).tar.gz --exclude='uploads/exports' -C /opt/miniwho uploads
```

恢复时停止后端，将备份的 `.db` 放回 `MINIWHO_DB` 指向的位置，并恢复 `uploads/`，再启动服务。

> 不要只复制正在写入的 `.db` 而忽略 `-wal` / `-shm`；WAL 中可能还有尚未合并的数据。

### 5.2 MySQL（手工部署）

```bash
mysqldump --single-transaction --routines --triggers \
  -h 127.0.0.1 -u miniwho -p miniwho > /backup/miniwho-$(date +%F).sql
tar czf /backup/miniwho-uploads-$(date +%F).tar.gz -C /opt/miniwho uploads
```

恢复：

```bash
mysql -h 127.0.0.1 -u miniwho -p miniwho < /backup/miniwho-2026-10-22.sql
```

### 5.3 Docker Compose

```bash
docker compose exec -T mysql sh -c \
  'mysqldump -uroot -p"$MYSQL_ROOT_PASSWORD" --single-transaction --routines --triggers "$MYSQL_DATABASE"' \
  > miniwho-$(date +%F).sql

docker run --rm \
  -v miniwho_uploads:/data:ro \
  -v "$PWD":/backup \
  alpine tar czf /backup/miniwho-uploads-$(date +%F).tar.gz -C /data .
```

如果 Compose 项目目录不叫 `miniwho`，用 `docker volume ls` 找到实际的 `*_uploads` 卷名。

4.1.2 的单容器 + SQLite 部署没有 MySQL，需要备份的只有 `miniwho-uploads` 卷（上面第二条命令），数据库文件与附件都在里面；恢复时把这个卷整体覆盖回去即可。用官方镜像跑 Compose 时，备份命令完全相同，只是不需要 `--build`。

恢复：

```bash
docker compose exec -T mysql sh -c \
  'mysql -uroot -p"$MYSQL_ROOT_PASSWORD" "$MYSQL_DATABASE"' < miniwho-2026-10-22.sql

docker run --rm \
  -v miniwho_uploads:/data \
  -v "$PWD":/backup \
  alpine sh -c 'rm -rf /data/* && tar xzf /backup/miniwho-uploads-2026-10-22.tar.gz -C /data'
```

### 5.4 升级

```bash
# 1. 先备份数据库与 uploads
# 2. 拉取新代码
git pull
# 3. Docker 部署
# 旧版本是 frontend + backend 两个容器，升级到单镜像时要用 --remove-orphans，
# 否则旧容器会继续占用 8088，新容器起不来。数据在 named volume 里，不受影响。
docker compose up -d --build --remove-orphans
docker compose logs -f app
```

单镜像会重建前端与后端，`docker compose up -d --build` 一步到位。手工部署则重新执行后端 `mvn clean package`，把新的 `frontend/dist` 覆盖到对外发布的目录后重启对应服务。

用官方镜像部署时不需要拉代码，换标签即可：

```bash
# 1. 先按 5.3 备份 MySQL 与 uploads
# 2. 把 compose 里的 image 改成新标签（保持 latest 则跳过）
docker compose pull app
docker compose up -d
docker compose logs -f app
```

单容器 + SQLite 部署则重新拉镜像，再用 4.1.2 里同一组参数重建容器，数据都在 `miniwho-uploads` 卷里：

```bash
docker pull cosolar/miniwho:1.0.2
docker rm -f miniwho
# 再执行 4.1.2 的 docker run
```

升级前可以先确认镜像对应的提交：

```bash
docker inspect --format '{{ index .Config.Labels "org.opencontainers.image.revision" }}' cosolar/miniwho:1.0.2
```

当前项目使用「启动时执行 `CREATE TABLE IF NOT EXISTS`」的方式初始化表结构，没有完整的版本化迁移工具。`resumes` 表新增列（如简历照片使用的 `avatar_key`、`avatar_shape`，首页示例使用的 `is_sample`）由后端 `SchemaMigrator` 在启动时自动 `ALTER TABLE ADD COLUMN`，因此数据库账号需要具备 `ALTER` 权限；SQLite 与 MySQL 都已覆盖。其余结构性变更仍请比对 `backend/src/main/resources/db/` 下的建表脚本，必要时手工执行 `ALTER TABLE` 或引入 Flyway / Liquibase。

`is_sample` 只加列、不建索引：存量库只走 `ADD COLUMN`，把索引写在建表脚本里会让新库与升级库的 schema 分叉，而这张表在自部署实例里体量很小，示例简历的读取（`WHERE is_sample = 1 AND deleted = 0`）全表扫描即可。存量库升级后默认没有任何一份简历被标上，前台会继续显示随代码打包的出厂示例，直到管理员在工作台点「设为首页示例」；首次部署由 `DataInitializer` 直接把演示简历标上。

模板表同样由 `SchemaMigrator` 补列：`pkg`、`namespace`、`version`、`author`、`source`、`api`、`checksum`、`owner_user_id`、`visibility`、`exportable`。首次升级到带模板包的版本时，启动日志里会出现若干条 `ALTER TABLE templates ADD COLUMN`，属正常现象。存量库升级后所有模板默认 `visibility = 'private'`、`exportable = 1`：官方模板不受影响（公开列表按来源放行），历史导入包则要作者在自己的「我的模板」页重新分享才会进模板中心。

#### 升级到带邮箱注册 / GitHub 登录的版本

新增三张表由建表脚本自动创建（`CREATE TABLE IF NOT EXISTS`）：`site_settings`（后台开关）、`user_identities`（第三方身份）、`email_codes`（一次性验证码）。`users` 由 `SchemaMigrator` 补两列：`has_password`（默认 1）、`email_verified`（默认 0，存量手填的邮箱一律算未验证）。

**升级会动数据，先按 5.3 备份。** 邮箱从「随便填的联系方式」变成了登录凭据，必须唯一，所以启动时会自动做一遍规范化：空串清成 `NULL`、全部转小写去空格；如果有多个账号共用同一个邮箱，**保留最早注册的那个，其余账号的邮箱被清成 `NULL`**，并在日志里 WARN 出被清掉的条数。这是为了让唯一索引建得起来，不是失败；被清掉邮箱的用户需要自己到个人中心重新绑定。索引已经存在时这一步直接跳过。

两件对使用者可感知的事：

- **注册入口默认全部关闭。** 升级后登录页上的注册按钮会消失，这是设计如此。想保持原来的开放注册，登录后门 `/admin` → 认证设置 → 打开「用户名注册」；想改成邮箱注册，先把邮件通道配好（后台「通道配置」或 `MINIWHO_MAIL_*`）再打开对应开关。
- GitHub 登录建出来的账号没有可用密码，`has_password = 0`；这类账号后续可以在个人中心（那里显示为「登录方式」）绑定邮箱，但**目前没有找回密码功能**，忘记密码仍只能由管理员处理。

### 5.5 模板包的归属、备份与升级

这套部署里模板有两个来源，写入路径互不干扰：

| 来源 | `templates.source` | 由谁决定 | 存放位置 |
| --- | --- | --- | --- |
| 官方模板 | `builtin` | 随应用发版的 `backend/src/main/resources/template-packages/*.json` | 打进 jar，启动时写回库 |
| 导入模板 | `imported` | 登录用户在「我的模板」页（`/my-templates`）导入模板包上传，归属记在 `templates.owner_user_id` | 数据库 `templates` 表 |

自部署场景下，导入者通常就是管理员本人（一个人一套部署）。多账号公开实例要知道这几件事：

- 导入的模板默认 `visibility = private`，只出现在**导入者自己**的「我的模板」里，公开列表（`GET /api/templates`）查不到。
- 作者在「我的模板」页打开「分享到模板中心」后，它才进入公开列表，变成本站所有用户都能选用的**社区模板**；关掉即从公开列表下架。分享只发生在这套部署站内，没有中央服务器，也不会上传预览图。
- 分享时还有一个 `exportable` 开关：`1` 时任何人（含匿名）都能 `GET /api/templates/{code}/export` 取走包原文，`0` 时非作者非管理员拿到 403，前端按钮换成「仅可使用」。
- 重新导入同命名空间同编码 = 原地升级，只对**同一个账号**生效，分享与导出权限沿用上次设置；编码被别的账号或官方占用时返回 409 `TEMPLATE_CODE_TAKEN`，不会静默覆盖别人的模板。管理员可以删除任意导入模板（仍在用则被拒绝），也可以停用模板强制下架。
- 取消分享不会破坏别人的简历：服务端仍按编码返回渲染配置（`GET /api/templates/{code}` 只卡 `status`，不卡可见性），那些简历继续原样渲染与导出，也能保存样式，只是不能再被新简历选中或换用。

升级时的行为（`DataInitializer.seedTemplates()`）：

- `source=builtin` 的行会被包文件**覆盖式刷新**（版式、名称、描述、标签、`sortWeight` 全部跟版本走），但管理员改过的 `status`（停用/启用）和用户用出来的 `usageCount` 不会被回滚。
- `source=imported` 的行**永远不会**被内置包覆盖，即使某次发版新增了同名模板。
- 导入模板的编码一定是 `命名空间--编码`（如 `acme--mypaper`），官方编码不带前缀，两者结构上就不会撞；`official` 这个命名空间被服务端直接拒绝，导入包冒用不了官方身份。唯一还可能走到「编码已被导入模板占用」这条日志分支的，是把老库里 `source` 手工改成过 `imported` 的行——真发生时要收回官方版式，先把那行删掉再重启。

因为导入模板只存在数据库里，备份规则很简单：

- **备份**：数据库备份（`mysqldump` / 复制 `miniwho.db`）就已经包含全部导入模板及其分享、导出权限设置，无需额外文件。想要一份可迁移、可对比的副本，用管理后台「模板管理 → 导出全部官方模板包」拿到一个 JSON 数组文件，或在「我的模板」/ 模板中心对单个模板点「导出模板包」拿到单个 JSON。`pkg` 列存的是净化后的包原文，导出的 JSON 可以直接在另一套部署里逐个导入（bundle 文件本身是数组，需要拆开后再导入）。
- **迁移到新部署**：把导出的 `.json` 逐个导入即可；跨版本导入时 `api` 字段会做兼容性检查，不认识的版本会直接拒绝而不是猜。
- **升级到新版官方模板后**，PDF 缓存不会返回旧版式：缓存键里带了模板的 `config` 字符串，重新导入或官方包刷新都会让键变化。如果发现缓存目录很大，可以直接清空 `exports/`（它只是缓存，随时可重建）。

如果一套部署希望「官方模板也归我管」，可以停用不需要的官方模板（后台点「停用」），停用只影响新建简历时的可选列表，已使用它的简历照常渲染。

## 6. 安全清单

公开部署前逐项确认：

- [ ] 修改或禁用 `demo` / `admin` 默认密码。
- [ ] `MINIWHO_SEED_DEMO=false`，并且已清理不需要的演示账号与示例简历。
- [ ] 数据库使用专用账号与强密码，只监听本机或内网。
- [ ] 后端 `8080` 不直接暴露公网，只由 Nginx 反代。
- [ ] 全站 HTTPS，分享链接同样使用 HTTPS。
- [ ] `MINIWHO_CORS_ORIGINS` 按需收紧为真实前端源；保留默认 `*` 时确认 API 没有依赖 Cookie 鉴权（本项目使用 `satoken` 请求头）。
- [ ] `MINIWHO_MEDIA_SECRET` 设置为独立的随机长字符串（不要复用数据库密码）。
- [ ] `MINIWHO_PDF_RENDER_BASE_URL` 指向的导出页只接受后端签发的一次性票据（5 分钟有效），确认反向代理与 CDN 不会缓存 `/export/*` 响应。
- [ ] 登录、注册接口配置限流；公网高流量场景加入 WAF 或验证码。
- [ ] 在 `/admin` → 认证设置里确认实际开放的注册方式符合预期：三个开关默认全关，只放开需要的那一种；用邮箱注册时确认授权码用的是邮箱**授权码**而不是登录密码（后台「通道配置」与环境变量都算，卡片上的来源就是当前生效的那一份）。
- [ ] 用 GitHub 登录时，站点对外地址与 OAuth App 的回调地址都指向对外 HTTPS 域名。Client secret 可以走环境变量（不进 Git 与 compose 明文提交），也可以填在后台——填后台等于明文存进 `site_settings`，那就得确认数据库本身没暴露出去。
- [ ] 定期备份数据库与 `uploads/`，并验证恢复流程。
- [ ] 上传目录与数据库文件不放入 Git 仓库，不通过 Nginx 直接静态暴露。
- [ ] 日志中不记录密码、分享密码或完整简历内容。
- [ ] 简历包含个人信息，遵守所在地隐私法规；公开分享前提醒用户检查隐藏字段。
- [ ] 若使用反向代理/CDN，确认其不会缓存 `/api/public/shares/*` 的私密响应。Nginx 默认不缓存代理响应，项目也未主动添加缓存头。

应用侧已有的防护：

- 密码与分享密码使用 BCrypt 哈希；
- 注册验证码同样只存 BCrypt 哈希（6 位数字明文抗不住库泄露后爆破），10 分钟过期、验证通过即删除、连错 5 次作废；发信按邮箱限到 60 秒 1 封 / 每小时 5 封，另叠加按 IP 的公开接口限流；发信失败与日志都不落收件人地址；
- GitHub 登录的 `state` 是一次性内存值（10 分钟过期、核销即失效），令牌只经 URL 片段交回前端并由前端立刻抹掉，服务端不出现在查询串与访问日志里；关联本地账号只认验证码验证过的邮箱；
- 服务端对富文本做 jsoup 白名单清洗，校验 URL 与月份格式；
- 分享时在服务端移除被隐藏的手机号、邮箱、微信、QQ、城市、主页与身份证字段；
- 附件扩展名、MIME、文件头校验，路径穿越防护，预览响应带 `nosniff` 与 CSP `sandbox`；
- 简历照片同样做文件头 + 解码校验，服务端压缩到最长边 600px、限制 3MB，只通过 HMAC 签名链接（6 小时）公开；
- PDF 导出使用 5 分钟一次性票据，简历数据只经 `/api/public/exports/{token}` 返回给渲染页面，不落到 URL 或日志；
- 导入的模板包只接受 JSON，`<style>` 里的 CSS 由 `TemplateCssSanitizer` 逐条规则重新生成后注入：注释先剥离、禁止 `<`、`@import`、`expression()`、`behavior`、`-moz-binding`、`!important` 与非白名单属性，`url()` 只收 `data:`，每条选择器必须以模板自己的作用域类开头，长度上限 16 KB。模板包格式里没有 HTML 与 JS 的位置，也不会有；
- 模板导入、删除、分享需要登录，导出全部模板包需要管理员；删除前服务端会检查是否仍有简历在用；
- 模板包的分享（`visibility`）与导出权限（`exportable`）由作者在「我的模板」页设置，服务端逐个接口判定：未分享的包不出现在公开列表、也不能被别人按编码选用（403），关闭导出权限后非作者取包原文返回 403（未登录 401）。前端只是把按钮藏起来，权限关卡在服务端；
- 简历内容乐观锁，避免多标签页覆盖；
- 统一异常响应，不向客户端抛出堆栈。

| `MINIWHO_PDF_BROWSER_PATH` | `/usr/bin/chromium` | 镜像内已预设，只有自己换浏览器时才需要覆盖 |

`MINIWHO_PUBLIC_BASE_URL`、`MINIWHO_MAIL_*`、`MINIWHO_GITHUB_*` 都能改在后台「通道配置」里填：后台填过的项优先于这里的环境变量，保存即生效，不用重拉容器（见 2.4）。

## 8. 常见故障

| 现象 | 排查方向 |
| --- | --- |
| `mvn: command not found` | 安装 Maven 3.8+ 并加入 `PATH`；或使用 IDE 内置 Maven |
| `Port 8080 was already in use` | 停掉占用进程，或修改 `WEB_PORT`（Compose 映射到宿主机）/ `SERVER_PORT`（直接跑 jar） |
| 后端启动后立刻退出 | 查看 `journalctl -u miniwho` 或控制台堆栈；确认 Java 17、数据库可达、上传目录可写 |
| 页面能打开但接口全部失败 | 检查 Nginx `/api/` 代理目标、后端健康和浏览器 Network；默认 `MINIWHO_CORS_ORIGINS=*` 不会因跨域拦截 |
| 浏览器报 CORS / 接口 403 `Invalid CORS request` | 说明把 `MINIWHO_CORS_ORIGINS` 收紧成了白名单且缺少当前来源；补上完整的 `协议://域名:端口`（或改回 `*`）后重启后端 |
| 登录后刷新变成未登录 / 401 | 令牌默认存内存，后端重启会失效；重新登录。检查 `localStorage` 是否被清理 |
| SQLite `database is locked` | 不要同时运行多个后端实例写同一个 `.db`；确认 WAL 文件可写；高并发改用 MySQL |
| MySQL `Communications link failure` | 检查 `DB_HOST`、端口、账号权限与防火墙；Compose 首次启动 MySQL 初始化需要时间 |
| 启动时报 `Table ... doesn't exist` | 确认 `spring.sql.init.mode=always` 且 schema 脚本被正确打包；手工建库时检查连接的是目标库 |
| 上传返回 413 或「文件超过大小限制」 | 同时检查 Nginx `client_max_body_size`、Spring `max-file-size` / `max-request-size` |
| Docker 应用一直 unhealthy | `docker compose logs mysql app`；首次 MySQL 初始化可能超过 40 秒，可适当增大 healthcheck `start_period` |
| Docker 上传文件后重启丢失 | 确认 `uploads` volume 已挂载；不要用 `down -v` |
| 附件 `Permission denied` | bind mount 时确保容器用户可写目录，必要时 `chown`；named volume 通常无需处理 |
| 刷新前端路由 404 | 镜像内置了 SPA 回落，出现该问题说明反向代理把请求直接写到了别处；手工部署则检查 Nginx 是否缺 `try_files $uri $uri/ /index.html` |
| 打印 PDF 排版不对 | 使用 Chrome / Edge，纸张 A4、边距无、勾选背景图形；预览页的缩放只影响屏幕，打印样式会恢复真实 A4 |
| 导出的 PDF 换页位置和预览对不上 | 正常不会出现：屏幕虚线、浏览器打印、服务端 PDF 用的是同一批断点标记。若确实对不上，先确认前端是最新构建产物（旧 `dist` 里没有分页样式），再检查是否用第三方工具二次转 PDF——那会重排页面 |
| 多页 PDF 的侧栏底色只出现在第一页 | 分页样式来自 `ResumePaper.vue` 的 `align-self: stretch`；确认部署的前端不是旧版本，且打印时勾选了「背景图形」 |
| 双栏模板导出的 PDF 比预览多一页 | 旧版分页脚本让正文列与侧栏列各断各的高度，整行因此多出一页。现在的落刀点要求同时是两列的空隙，只用最新 `dist` 即可 |
| 点「下载 PDF」提示引擎不可用（`PDF_ENGINE_UNAVAILABLE` / 503） | `GET /api/pdf/status` 看 `engine` 字段：`not-configured` 表示没设 `MINIWHO_PDF_RENDER_BASE_URL`；`none` 表示找不到浏览器，安装 Chromium 或设置 `MINIWHO_PDF_BROWSER_PATH`。前端会自动退回浏览器打印，功能不中断 |
| 服务端 PDF 能生成但中文是方块 / 空白 | 宿主机或镜像缺中文字体。Alpine 加 `font-noto-cjk`，Debian/Ubuntu 装 `fonts-noto-cjk`，重启容器或后端 |
| 服务端 PDF 报「生成失败，请检查渲染地址」 | 后端进程访问不到 `MINIWHO_PDF_RENDER_BASE_URL`（容器网络、自签 HTTPS、页面服务未启动都会命中）；单镜像保持默认 `http://127.0.0.1:8080`，前后端分离时填前端容器地址，不要用 `localhost` 指代别的容器 |
| 服务端 PDF 报「生成超时」 | 页面依赖的资源加载过慢，调大 `MINIWHO_PDF_TIMEOUT`；同时确认渲染地址返回的是最新前端构建 |
| 简历照片刷新后看不到 | `MINIWHO_MEDIA_SECRET` 未固定，后端重启后旧签名链接失效；刷新页面会重新签发，若持续 403 请设置固定密钥 |
| 分享页看不到照片 | 先确认这份简历上传过照片：所有版式都会渲染，位置随版式不同（多数在页眉右侧，居中版式在姓名上方，侧栏版式在左栏顶部）；若图片请求 403，按上一行处理签名过期 |
| 分享链接 410 | 链接已过期、已撤销，或简历已删除；重新生成分享链接 |
| 分享密码正确仍 401 | 确认请求的是 `/unlock` 接口；密码区分大小写；重新创建链接可重置密码 |
| 改了 `MINIWHO_ADMIN_PASSWORD` 但登录不上 | 该变量只在首次创建账号时生效；使用当前密码登录后在个人中心修改，或重建管理员账号 |
| 登录页没有注册入口 | 正常：三种注册 / 登录方式默认全关。进 `/admin` → 认证设置打开，开关需要与凭据同时成立 |
| 后台打开了邮箱注册开关，报「邮件通道尚未配置」 | `MINIWHO_MAIL_HOST` / `MINIWHO_MAIL_FROM` / `MINIWHO_MAIL_PASSWORD` 有空的（后台那一份没填，环境变量也没兜住）；在「通道配置 → 邮件通道」补齐后保存即可，不用重启 |
| 邮箱一直收不到验证码 | 依次确认：授权码填的是**邮箱授权码**（不是登录密码，后台或环境变量都算）、SMTP 服务已在邮箱网页端开启、465 端口对应隐式 SSL（587 要改成 `ssl=false` + `starttls=true`）、宿主机出站 465/587 没被云厂商安全组拦掉。后台卡片上写的来源就是当前真正生效的那一份。后端日志只有一行 `邮件发送失败：...`，具体原因看它 |
| 注册时提示「该邮箱已注册」但本人说没有 | 邮箱在库里唯一，`admin` 初始化时占用了 `admin@miniwho.local`；先确认有没有别人占用，确需释放则由管理员清空该账号的 `email` 后请用户重新绑定 |
| GitHub 授权后回到登录页并报「登录未完成」 | 回调地址与站点对外地址（后台填的或 `MINIWHO_PUBLIC_BASE_URL`）拼出来的那条不一致，或 `state` 已过期（超过 10 分钟、后端重启都会失效）；以后台「认证设置」显示的回调地址为准，在 GitHub OAuth App 里改成一模一样 |
| GitHub 授权页直接报 `redirect_uri_mismatch` | OAuth App 的 Authorization callback URL 少了 `/api` 前缀或末尾多了斜杠；正确形式是 `https://<域名>/api/auth/oauth/github/callback` |
| 用 GitHub 登录后没关联到原来的邮箱账号 | 自动关联只认**验证码确认过**的邮箱，存量手填邮箱一律算未验证，这是防接管的设计。这种账号只能继续用密码登录；在个人中心改绑邮箱会把验证状态归零，也不会因此获得关联 |
| 管理后台显示 403 | 当前账号 `role` 不是 `admin`；按第 3.1 / 4.3 节在数据库中提升角色并重新登录 |
| `docker pull` 长时间无进度 / 超时 | 本机到 Docker Hub 不通或限速：给 Docker 配置镜像加速或走代理；`docker manifest inspect cosolar/miniwho:1.0.2` 可以先测连通性，不必拉完整镜像 |
| 容器一启动就退出，日志里有 `exec format error` | 镜像只有 `linux/amd64`。Apple Silicon / arm64 机器改用 `--platform linux/amd64`，或换 amd64 服务器 |
| 单容器重启后账号、简历全没了 | 没挂卷，或没把 `MINIWHO_DB` 指到卷里；数据库默认写在容器内的 `/app/miniwho.db`，容器删除即丢失。按 4.1.2 加 `-v miniwho-uploads:/app/uploads -e MINIWHO_DB=/app/uploads/miniwho.db` |
| 用官方镜像后服务端 PDF 提示「生成失败，请检查渲染地址」 | 多半是覆盖了 `MINIWHO_PDF_RENDER_BASE_URL`。单镜像保持 `http://127.0.0.1:8080`，只有把前端拆到别的容器 / 域名时才改 |
| `docker run` 报 `port is already allocated` | 宿主机端口被占用，换 `-p` 左侧端口；`docker ps` 里旧容器也会占着 8088 |
| 时间显示差 8 小时 | 后端固定 `Asia/Shanghai`，容器建议设置 `TZ=Asia/Shanghai`；浏览器按本地时区渲染 |
